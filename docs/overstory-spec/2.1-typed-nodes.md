# Typed nodes

A node with a schema is a **typed node**: its children are pages whose
properties are typed fields. Each child is a node like any other, read at a path,
linked to and shown as a page; the schema adds that its name comes from its key,
its fields must match their declared types, and its connections to other
children are kept consistent at both ends. A typed node's children are all of
its declared types.

A typed node's children are logical state whose history the tree holds as a log
([§1](#1-what-the-tree-holds)), in the canonical form of [§2](#2-children-and-values),
and every file or database that shows them is one placement's
[projection](6.2-placements-on-disk.md#4-projections) of that state. Two
placements of one tree may project children differently, and both hold the same
children and the same root.

The node's [schema](2.3-beetle-tables.md#5-a-typed-nodes-schema) is a file
object with exact bytes, named by the node's `schema` member
([data model §5](1.1-data-model.md#5-objects)); a placement spells it
`schema.beetle` in the node's folder. The node keeps its own page (`games.md`
beside its folder, or `games/_index.md`). The children of the schema's
[`main` table](2.3-beetle-tables.md#1-tables-and-fields), if it has one, are
the node's children. Every other table that holds data is a child named after
its table, whose children are that table's. A typed node's children have no
children of their own yet; a type that declares its own children's types is a
planned extension.

Interpreting a typed node never executes authored code. The schema is data: a
conforming implementation parses and checks it under the language's finite
limits and validates children against it without inserting defaults or
transforming values. The schema is the whole contract for a typed node's
children: anything a projection holds that the schema doesn't declare, such as
an extra CSV column, JSON key order or a comment in a Markdown child's front
matter, is that placement's own and does not cross to another placement.

## 1. What the tree holds

```text
The node /games:
  page     → pageHash            (an ordinary page)
  schema   → schemaHash          (spelled games/schema.beetle)
  children → log entry → entry → … → snapshot entry → SQLite file
Children of /games (Game is the main table):
  chess, go
  List/favorites
```

A typed node's children are held once, by its host, in a database; the tree
holds the node's **log**: its accepted child changes, in order. The node's
`children` names the log's head entry, and the log's objects are defined in
[data model §5](1.1-data-model.md#5-objects). Each entry names the one before it and holds either the child changes of
one accepted update or a snapshot:

- A **changes** entry lists each child the update changed, once, as its whole
  new [§2](#2-children-and-values) form, or as removed. Its children are the previous
  entry's children with these applied. Merging has already happened when an entry
  is written ([§4](#4-accepted-update-validation-and-merge)): an entry holds
  outcomes, never authored operations, and applying one needs no schema.
- A **snapshot** entry names a file object holding every child as of that
  entry: a SQLite database implementing the schema's
  [database layout](2.3-beetle-tables.md#52-layout) under its own names, with no
  storage mapping. Its bytes are whatever the host's SQLite wrote; only its
  children are compared. Only the tree's host writes snapshots, so every placement
  holds the same entries.

Every entry carries the **children hash** and child count after it. The children hash is
LtHash16 ([Lewi et al., 2019](https://eprint.iacr.org/2019/227)) over the children:
each child contributes SHAKE256 of the canonical CBOR of `[table, child]`, 2,048
bytes read as 1,024 little-endian 16-bit lanes, and the state is the lane-wise
sum of every child's contribution modulo 2<sup>16</sup>. `childrenHash` is the
SHA-256 of the state's 2,048 bytes. A change takes out a child's old
contribution and adds its new one, so keeping the hash costs one contribution
per changed child, and any store can check it, since it is defined over children,
not bytes. The empty typed node's state is all zeros.

The typed node's **logical hash** is the canonical CBOR hash of
`{ modelFingerprint, childrenHash }`, the
[schema fingerprint](2.3-beetle-tables.md#53-fingerprints) of its schema and the
children hash of its head entry. It is the children's contribution to the node's
model hash: the same for the same
children, whatever history led there and however a placement holds them. The
root, as for any object, commits to the log itself.

An authority checks a log by applying it: from a snapshot entry, it opens the
file, reads its children, and requires their count and children hash to equal the
entry's; then it applies each later entry in order, requiring the same after
each. It also requires:

1. The node's schema to parse and check under the language's limits.
2. Every object to decode canonically, every changes entry to name each child
   at most once and only tables that hold data, and every removed child to be
   present.
3. Every child of the head state to validate against its table
   ([§2](#2-children-and-values)), and every reference to name an existing child or
   enum value.

Then it exposes the head state's tables as the node's children. A host accepting updates checks each new entry as it writes it, so a
full check is needed only for a log that arrives from elsewhere: a tree a host
takes over, or a backup restored.

### 1.1 Snapshots and history

Walking objects from a root reaches the log's head entry and every entry
before it back to the newest snapshot entry, and that snapshot's file: a
snapshot walk, a snapshot bundle and a copy of a tree all stop there, and need
no other route. A snapshot entry's `previous` may name entries the host no
longer keeps.

The host writes a snapshot entry when the changes since the last snapshot
outgrow the database, with no child changes and the same children hash as the entry
before it, in an accepted update it makes itself with no other effects. A host
keeps entries and snapshots for its history budget. A typed node may keep less
history than pages: reading a typed node at a root whose state the host can no
longer rebuild from a snapshot it keeps answers `410 not-retained`.

A host advertises its child and entry quotas.

## 2. Children and values

A child's [§2](#2-children-and-values) form is a map with `key`, `fields`, `created` and `modified`:

- **`key`** is its table's key ([Beetle tables §4](2.3-beetle-tables.md#4-keys))
  as an array of `[field, value]` pairs in key order. Its canonical key JSON
  is the child's stable key ([locators](1.4-locators.md#2-stable-keys-revisions-and-fragments)),
  immutable under an ordinary child update; changing it is removal of one child
  and creation of another. Its logical name is [§3](#3-child-identity-and-order)'s.
- **`fields`** holds every other declared field that has a value, by name.
  An optional field without a value and an empty many-valued field are
  absent, never `null` or empty.
- **`created`** and **`modified`** are Unix milliseconds in UTC, like a
  file entry's or a node's times
  ([data model §6](1.1-data-model.md#6-entry-times)). They are stamped from accepted operations' `at`, and
  never set directly ([updates and merging §2.5](1.3-updates-and-merging.md#25-property-operations)).

Values have one canonical form per type, so no projection's conventions
reach the tree: `Text` and `Markdown` are UTF-8 strings, `Int` is a CBOR
integer, `Number` is a number in canonical CBOR (an integral value is
encoded as an integer, so `1` and `1.0` are one value; the schema, not the
encoding, says which type a field has), `Bool` is a boolean, a `Date` is a date or a date-time tagged as in a page
property (tag 1004 around `YYYY-MM-DD`, tag 0 around an RFC 3339 date-time in
UTC), so children and pages spell dates one way and a date is never a plain
string, a reference to another child is the target's key value (an array
of its pairs when the key has several fields), a reference to an enum is the
value's name, a `Person` is a profile TreeID or a `contact:` placeholder
([Beetle tables §1](2.3-beetle-tables.md#1-tables-and-fields)), and a value array is an array.

Only tables' children are addressable: `/games/chess` for the main table and
`/games/List/favorites` for another, a connection table's children included. A plain n:m connection is not a node set. It is a set of pairs held once,
as a field on the children of one end: the `ordered` end, else the end declared
first. The other end shows it as a field derived from those pairs, and either
end's child operations change the same pairs. An `ordered` field is a sequence
of member keys, never position numbers. A 1:1 or 1:n connection is a
reference on its single side.

A child has no content outside its fields. A Markdown projection's body and
title are fields ([Beetle tables §5.1](2.3-beetle-tables.md#51-layers-and-attributes)).

## 3. Child identity and order

- **Child name.** A child's path segment is the value of its table's
  field marked `path` ([Beetle tables §1](2.3-beetle-tables.md#1-tables-and-fields)),
  which must be one valid logical `Name`. Without such a field it derives from
  the key, as below.
- **Child identity.** A typed node's declared primary key is the
  stable-key rule for its children. It must be stable, non-null,
  serializable, and independent of child position, SQLite `rowid`, display
  label, or query plan. A child's third reference component is its canonical key
  JSON as defined by
  [locators](1.4-locators.md#2-stable-keys-revisions-and-fragments); each key
  field's validated value must be a JSON string, boolean, or finite number.
  Key values are already in that form ([§2](#2-children-and-values)). Changing a key is observed as
  removal of one child and creation of another. A child's key-derived segment
  is its single string key when that is a valid nonempty logical path component
  not beginning with the reserved `~row-` prefix; otherwise it is `~row-`
  followed by the unpadded base64url encoding of the canonical child key. This
  is the one surface that still uses base64url rather than the locator key
  token; the rule is under review in
  [Postgres 001](../../plans/later/postgres-001-postgres-backed-collections.md#open-from-the-old-plans).
- **Ordering.** Projected and database children enumerate in canonical stable-key
  order, falling back to canonical path, using the portable comparison; a
  backing's default collation is not an acceptable substitute. Where a
  relational extension supplies explicit ordering, the proved stable key is the
  deterministic final tie-breaker.

## 4. Accepted update validation and merge

An update changes a typed node by child operations, which the host replays on
its basis children; a client that does not encode a typed node's tables leaves the
resulting roots out and the host derives them
([updates and merging §2.3](1.3-updates-and-merging.md#23-derived-candidates)). A snapshot
update (a `null` trace) that changes a typed node is accepted only from a
caller allowed to `write` the typed node's path, and its effects are the child
differences from its basis. The host validates all keys, references and
constraints, merges concurrent changes by
`child-fields-v1` ([updates and merging §3.6](1.3-updates-and-merging.md#36-merging-properties)),
appends one changes entry with the children the accepted update changed
([§1](#1-what-the-tree-holds)), and never trusts a client-supplied fingerprint
or hash. An update that changes no child appends no entry.

A merge conflict on a field becomes a decision scoped to that child field
([conflicts §2](4.2-conflicts.md#2-reading-conflicts)); a
merged result the schema rejects is a conflict on the typed node.
Changing the schema's data layer, a schema migration, is not yet specified
([Schema Language 009](../../plans/features/schema-language-009-schema-changes-keep-the-data.md)).

## 5. Value validation and limits

Validation is a pure decision over one child. A child matches its table when
every required field is present, every value has its field's type and arity
([§2](#2-children-and-values)), every reference names an existing child or enum value, and `unique`
fields are unique. Diagnostics name a stable code (`type-mismatch`,
`missing-member`, `no-matching-choice`, `invalid-text`, `budget-exceeded`)
and the failing field, in the order fields are declared. The
[`collection-schemas.json`](conformance/collection-schemas.json) vectors bind
this section.

[Beetle's limits](2.2-beetle.md#5-limits-and-diagnostics) apply to the
schema. Validating one child takes at most 1,000,000 steps (values visited plus
map members examined), and one typed node at most 50,000,000; exceeding
either rejects the child or the update with `budget-exceeded` naming
`child-steps` or `children-steps`. The quotas of [§1.1](#11-snapshots-and-history) apply in addition.
