# Views

A **view** is a view tree whose elements may carry reads. `view Name(params):` declares
a named view, which other views draw as an element `<Name …/>`, and `view(params):` a
file's unnamed view, which the file draws when visited ([Beetle §2](2.2-beetle.md#2-beetle-files)):

```
view PracticeCard(p: Practice):
  <Column style="card">
    <Text style="heading">{p.name}</Text>
    <Markdown source={p.about} lines={6} />
  </Column>
```

A parameter is written as it is given in a call, `name: Type`, with a type from
[Beetle tables §1](2.3-beetle-tables.md#1-tables-and-fields) (`l: List`, `name: Text?`, `tags: Text[]`), just as a call
writes `name: value`. A parameter with no
type is text. A parameter typed with a table takes a row; given a key, from a query string
or a form, it resolves the key to the table's row, and a key with no row the caller can
read is `missing`.

A view's body is one element, optionally preceded by `state`, `keep` and event lines
([§6](#6-state), [§7](#7-actions-forms-and-events)), or, in a **data view**, a
record in braces that a host returns as JSON ([§8](#8-data-views)). Its parameters are its input: from
the query string when it is visited at its address ([§13](#13-view-addresses)), and from
attributes when it is drawn as an element ([Beetle §3](2.2-beetle.md#3-using-other-files-and-views)).

A view's **plan** is every read in it and in the views it draws, found by checking the
file, not by running it ([§12.2](#122-plans-and-live-dependencies)). What the host
reads depends only on the view's input and the user. Conditions that read state are
evaluated on the viewer's device instead ([§6](#6-state)).

## 1. Elements

An element is `<Type attributes>children</Type>` or `<Type attributes />`. `Type` is a
named view the file declares or uses, or one of the element types every client draws
([§9](#9-element-types-and-layout)). An attribute is `name="text"`, `name={expression}`, or a bare `name`, meaning
`name={true}`. Text children may hold `{expression}`, and so may quoted attribute text:
`subtitle="@{person.handle}"`.

These attributes belong to the language, on any element:

| Attribute | Means |
|---|---|
| `for={name in source, …}` | introduce names and expand ([§4](#4-expansion)) |
| `where={condition, …}` | conditions on the matches of the element's `for` ([§3](#3-conditions-and-rules)) |
| `if={condition, …}` | on an element without `for`: draw it only when the conditions hold |
| `orderBy={expression [desc], …}` | order the matches; ties fall back to canonical order |
| `group={expression}` | group the matches by the expression's values; a match is in each group its value reaches |
| `limit={n}` | keep the first `n` matches |
| `fallback={element}` | drawn when the element expands to nothing or its conditions fail |
| `key={expression}` | the element's identity among its siblings; defaults to the row keys of its names |

`where` goes only with `for`, and `if` only without it; either in the wrong place is a
check error. A view tree is plain `{type, props, children, key}` data. `Markdown` renders
a Markdown source string with Overstory's ordinary link resolution, safe URL and asset
policy, and source semantics. It is the standard way for a view to present stored
Markdown. It resolves a relative Markdown destination from the directory holding the
file, as [locators §2.1](1.4-locators.md#21-links-written-in-markdown) defines. For a
destination carrying the reserved `#overstory-key=` alias, it emits the equivalent
server-visible path suffix and preserves the authored application query. It does not
forward the reserved identity alias as an HTML fragment.

**`Rows`** is the standard element for a list of rows that a reader can edit in place. It
draws one line per match of its `for`, with its children as the line's cells, grouped
under a heading per value of `group` when it has one (a row with several values appears
under each), and ordered by `orderBy`:

```
<Rows for={l in List} group={l.owner} orderBy={l.modified desc}>
  <Bullet value={l.visibility} />
  <Text>{l.name}</Text>
  <Count of={l.items} />
</Rows>
```

A client may draw a `Rows` as its own native, editable list. A cell that shows one of the
matched row's own fields, or the rows a connection field reaches, edits that field or the
connection; regrouping a row writes its `group` field when that is one of its own fields.
A cell computed from other rows, such as a count or the latest of several dates, is
read-only. A field whose table is a **connection table** keyed by exactly its two ends
(`Item` between a list and a practice) shows and groups by what it connects to: a list's
`items` are its practices, in the connection's order, and connecting or regrouping writes
the connection's rows. Any other row whose key has several fields (`Tag (list, id)`) is
named by its whole key. A `Bullet` cell draws a value as a colored dot with its name,
colored by the value's own `color` field when its table or enum has one, unless the
element gives `color={…}`. The cells a client draws natively, and how a `Rows` with other
cells is drawn, are in [§9](#9-element-types-and-layout).

## 2. Reading rows

`for` on an element introduces names and the rows they range over:
- **A table's rows:** `for={l in List}`.
- **A relationship's rows,** from a name already bound: `for={t in i.practice.tags}`.
- **Several names,** separated by commas; a later one may range over an earlier one:
  `for={p in Practice, other in p.authors}`.

A **path** follows fields from a bound name: `l.owner.name`, `i.practice`. A path
through a to-many field reaches every row it leads to, without duplicates:
`l.items.practice.authors` is everyone who wrote a practice on the list. Paths may
be read anywhere an expression is allowed, and a plain relationship read needs no
`for`: `<Image person={l.owner} />`.

## 3. Conditions and rules

`where` holds the conditions a match must meet, as boolean expressions joined by
commas, which mean *and* ([Beetle §4](2.2-beetle.md#4-expressions-and-built-ins)):

| Condition | Means |
|---|---|
| `l.visibility == Public` | a field equals a value; an enum value is written by name |
| `q in p.name` | a text field contains text |
| `l.owner == person` | a to-one relationship points at a row, a key, or `null` |
| `person in p.authors` (`person ∈ p.authors`) | a to-many relationship includes a row or a key |
| `p.authors excludes person` (`person ∉ p.authors`) | it doesn't |
| `person in l.items.practice.authors` | a path: some item's practice has this author |
| `a or b`, `not a` | alternatives and negation |
| `curatedBy(l, person)` | a **rule**: a named condition defined once |

Each condition is a fact over the names in scope, and a name that appears in two
facts joins them. A view's reads are its facts: there is no other narrowing, and
nothing else in a view decides which rows it reads.

A **rule** is a named condition, usable in any `where` or `if`. Its body's lines are
conditions joined by *and*, and two rules with the same name and parameters are
alternatives, joined by *or*:

```
rule curatedBy(l: List, person: Person):
  l.owner == person
rule curatedBy(l: List, person: Person):
  person in l.contributors.person
```

A rule may not refer to itself, directly or through other rules.

There are no per-table read rules. What a view may read is what its caller may read
([access control §4.3](5.2-access-control.md#43-authority-and-consent)), and rows that some readers must not see live in a
tree those readers can't read ([access control §4.4](5.2-access-control.md#44-data-disclosure)).

`orderBy` orders an element's matches, `group` groups them and `limit` cuts them
([§1](#1-elements)). All three are part of the plan.

## 4. Expansion

An element with a `for` **expands**: it appears once for each distinct combination of
values of the names it introduces and uses, in its attributes, its text or anywhere
among its children. A name it introduces but uses only in `for` and `where` joins
without multiplying the element. So

```
<Image person={other}
  for={p in Practice, other in p.authors}
  where={person in p.authors, other != person} />
```

draws one portrait per collaborator, while a `Text` that shows both `{other.name}` and
`{p.name}` draws one line per pair.

An element with `if` appears when its conditions hold and not otherwise.
`fallback` gives what to draw when an element expands to nothing or its conditions
don't hold.

Inside an element, the names its `for` binds are fixed. A nested element's reads
therefore run once per match of its ancestors, and the result is tree-shaped:
`<Text style="tag" for={t in i.practice.tags} where={t.list == l}>` inside an expansion over a
list's items draws each item's tags for that list.

A name that no `for` binds and no parameter or state declares is a check error.

## 5. View blocks in pages

A fenced code block whose info string is `view` holds declarations and at most one
element on its own, which draws where the block sits:

````md
# Today

```view
<Text>{count(c in page.children where c.done)} of {count(page.children)} done</Text>
```

```view
view Late():
  <Column>
    <Text for={c in page.children} where={not c.done, c.due < page.date}>{c.name}</Text>
  </Column>
```
````

- **All of a page's view blocks are one file** ([Beetle §2](2.2-beetle.md#2-beetle-files)): a
  name declared in one block is usable in every other, and an import in any block applies to
  all. Other files use a page's named views, rules and mutations with `import Today.md`.
- **A block's own element** is an unnamed view with no parameters, drawn where the
  block sits. `view(params):` in a block is the same with parameters, and
  `view Name(params):` adds an address, `Today?view=Late` ([§13](#13-view-addresses)).
  Unnamed views on a page take the page's query string as their input.
- **A named view without parameters also draws where its block sits.** One with
  parameters draws only where it is drawn as an element or addressed, and a block holding
  only those, rules, mutations or state tables draws nothing.
- **`page`** is the page a view is drawn in: the page holding the view block that draws
  it, or the view's own node when it is visited by itself. Its fields are the page's
  properties, read as their values with no schema, plus `name`, and `page.children` is its
  child nodes, each read the same way. Reading `page` is a read like any other: it joins
  the plan and is a live dependency.

A page's prose stays non-executable Markdown: a page runs nothing because it links a
view. A client that doesn't evaluate views shows each block as code. Story shows a block's
source while it is being edited and its drawing otherwise.

## 6. State

A view's state is rows of **state tables**, declared with `my table X:` or
`session table X:` like any table ([Beetle tables §1](2.3-beetle-tables.md#1-tables-and-fields)), but beside the views
that use them, in any `.beetle` file or view block. Their rows are not in any typed node
folder, and a state table can't be `main` or an end of a connection that a data table
also ends; its fields may refer to data tables' rows. State tables belong to one viewer
and differ in how long they last:

| | kept | this session |
|---|---|---|
| **one viewer** | `my table`, `keep` | `session table`, `state` |

- A **`my` table** holds one viewer's own rows, across the app. Its rows are read and
  written only by their viewer, need no consent, and are written on the viewer's device
  first.
- A **`session` table's** rows are never stored and live for one viewer's session on one
  device. They suit fast-changing state, such as the positions in a game.
- A state table is declared beside the views that use it, in the same file or view block:

  ```
  my table Lap:
    at:    Date
    label: Text

  mutation lap(label: Text):
    Lap(at: now, label: label)
  ```

- `state x = value` in a view declares a one-row session table with one field, and
  `keep x = value` a one-row `my` table per **spot**, where a spot is one view
  block's drawing in one page, and a view visited on its own has one spot per
  address. Both are read by name like a parameter and changed with `set(x, value)`
  ([§7](#7-actions-forms-and-events)). A view drawn as an element inside another view
  has its own `state` and `keep` for each instance, told apart by the element's `key`.

There are no tables shared by everyone at one spot. A widget's configuration is its
view block's attributes (`<Timer minutes={50} />`), and rows that several people share at
one place are ordinary data, with a field saying which place.

A view reads state the way it reads any rows, and changing state reevaluates only the
expansions that read it.

**State never leaves the viewer's device.** Checking splits each read: the conditions,
orderings and paths that don't read `state`, `keep` or a state table form the plan the
host runs, and those that do are evaluated by the client over the rows the host returns.
So a host never learns state, and a state change redraws without a request. Inputs are
the opposite: they are what the host sees and what a URL carries. A view that wants the
host to filter by a value, for example a search over many rows, takes it as an input
(`?q=…`), which also makes it linkable. A `limit` on an element whose conditions or
ordering read state is a check error, because the host can't cut what it can't order;
the value must be an input instead.

A viewer's `my` rows, `keep` values among them, are stored in a private tree of the
viewer's own that only they can read, created the first time a view writes one, in one
folder per app: `apps/<TreeID>/`, named by the tree that holds the declaring file. They
reach the viewer's other devices as that tree does. They are never stored in the viewer's
profile tree, which others read ([access control §4.4](5.2-access-control.md#44-data-disclosure)).
How a client finds that tree is not yet specified
([Apps 011](../../plans/soon/apps-011-widgets-in-story.md)).

## 7. Actions, forms and events

An **action** is a call written as an attribute value: a mutation with its input,
`addPractice(name: n)`, or `set(x, value)` for state. `Button action={…}` runs one when
pressed. A client runs a mutation action with a stable mutation identity and exposes
pending state, then its result, durable receipt, or public error.

A **form** gathers a mutation's input from controls. `<Form action={addPractice(list: l)}>`
names a mutation and may give some of its arguments; each control in the form with a `name`
gives the parameter of that name, converted and validated by the parameter's type, not
as text. A parameter neither given nor named is absent, and a name that is no parameter is
a check error. Pressing a `Button` in the form that has no `action` of its own, or Return in one of its text fields, runs
the action. While it runs the form's controls are disabled; on success they return to their
`initial` values (empty when none is given); on `invalid`, each field error is shown at the
control that gave that parameter. A form needs no state, so a browser can run one with no
script. `then={action or link}`, on a `Button` or a `Form`, runs or navigates after success.
Expected failures are a mutation's public errors
([mutations §2](3.2-mutations.md#2-public-errors)), input validation among them. Server exceptions, private
values and stack traces never become action state.

A **control** is an element a reader changes: a `TextField`, a `Toggle`, a `Picker`, or
a `Text` marked `editable`. Its `value` says what it shows and where a change goes:

- **State.** `value={x}`, naming state, binds the control to it in both directions; a
  change sets the state, and nothing else runs.
- **A row's field.** `value={t.done}` shows the field and is read-only unless the control
  has an `action`. A change runs the action with the new value filling the mutation's
  parameter named after the field, so `<Toggle value={t.done} action={setDone(t)} />`
  runs `setDone(t, done: true)`. The mutation must have that parameter, of the field's
  type, and must not be given it in the call; otherwise it is a check error. Rows change
  only through mutations, so this is the whole write path: while the action runs the
  control shows the new value, and on a public error it returns to the field's value and
  shows the error at the control.
- **In a form.** `name` instead of `value` makes the control give that parameter of the
  form's action, starting from `initial`, as above.

A `TextField` or an `editable` `Text` commits on Return or when the reader leaves it, and
Escape puts back the value it started from; a `Toggle` or `Picker` commits on each change.
`<Text editable value={t.title} action={rename(t)} />` reads as ordinary text until the
reader clicks it, then edits in place.

A view may name actions for events a client delivers, one per line before its element:

```
on key "ArrowLeft" → movePaddle(-12)
every 16ms → step()
```

A client delivers them only while the view is shown, and at most as often as it can draw.
The view still has no clock: an event can only run an action.

## 8. Data views

A **data view** returns JSON instead of drawing. It is declared like any view, with `{`
after its parameters instead of `:`, and its body is the shape of the JSON it returns.
An entry that holds braces takes the attributes a UI element takes, `for`, `where`,
`orderBy`, `limit` and `if` ([§1](#1-elements)), between its `key:` and its braces, where an
element has them between its type and its children:

```
view ListsByOwner(owner: Person) {
  lists: for={l in List} where={l.owner == owner} orderBy={l.modified desc} limit={20} {
    name
    size: count(l.items)
    owner: { name, handle }
    practices: for={p in l.items.practice} orderBy={p.name} { name }
  }
}
```

returns `{ "lists": [{ "name": …, "size": …, "owner": { "name": …, "handle": … },
"practices": [{ "name": … }] }] }`. Converting between the two is mechanical:
`<Row for={l in List}>…</Row>` and `lists: for={l in List} { … }` read the same rows,
and `{l.name}` in an element's text is `name` in a data view's braces. Inside braces,
entries are separated by line feeds or commas, and each is one of:

| Entry | Gives |
|---|---|
| `key: expression` | the expression's value; a path through a many-valued field is a list |
| `key: for={x in source} where={…} orderBy={…} limit={n} { … }` | a list, one record per match, with the attributes meaning what they mean on an element; the record's bare fields are the match's |
| `key: path { … }` | follows the path from the row the enclosing braces are about: a record for a to-one path, `null` if it reaches none, and a list for a to-many one |
| `field`, `field: { … }` | shorthand for `field: field` and `field: field { … }`: the field of that row, under its own name; a bare relationship gives the key, or a list of keys, of the rows it reaches |
| `key: if={condition} { … }` | the record when the condition holds, and `null` otherwise |

The outermost braces are about no row, so their entries need a `key:`. A data view has
parameters, rules, a plan, an address and live results exactly as a UI view does, and it
has no state, actions or events. A host answers it with its JSON
([§12.1](#121-answer-forms)), and a client
may show that JSON with its own default presentation.

## 9. Element types and layout

Every client draws these element types:

| Type | Draws |
|---|---|
| `Text` | its text children, with `{expression}`s filled in |
| `Markdown` | a Markdown `source` string ([§1](#1-elements)) |
| `Link` | its children as a link to `to` |
| `Image` | an image from `src`, or a person's portrait from `person={…}` |
| `Button` | its children; runs `action` when pressed ([§7](#7-actions-forms-and-events)) |
| `Text` with `editable` | its text, edited in place when clicked; a control ([§7](#7-actions-forms-and-events)) |
| `TextField` | a one-line text input; a control, with `placeholder` shown while empty |
| `Toggle` | a switch for a `Bool`, with its children as the label; a control |
| `Picker` | one choice among `options={list}`, or among an enum's values when its `value` or `name` is of an enum type, with its children as the label; a control |
| `Form` | its children; the controls in it supply its `action`'s input ([§7](#7-actions-forms-and-events)), so a browser can run a mutation with no script |
| `Column` | its children top to bottom |
| `Row` | its children side by side, wrapping onto new lines when they don't fit |
| `Rows` | a list of rows a reader can edit in place ([§1](#1-elements)); a client draws only the lines on screen |

Any other type is a named view the file declares or uses, and a type that is neither is a
check error. A client draws a `Rows` as its own native list only when every cell is a
`Bullet`, `Text`, `People` (the people a field names, as portraits), `Count` (how many
rows `of` reaches) or `Date`. Otherwise it draws the whole `Rows` as a `Column` with a
`Row` of cells per line, under a `Text` heading per group, and no cell edits in place.

These attributes lay elements out:

| Attribute | On | Means |
|---|---|---|
| `spacing="step"` | `Column`, `Row`, `Rows` | the gap between children: `none`, `small`, `medium` or `large` |
| `start`, `center`, `end` or `stretch` | a child of a `Column` or `Row` | where the child sits across the direction its parent flows in; by default a `Row`'s children are centered and a `Column`'s sit at the start |
| `grow`, `grow={n}` | a child of a `Column` or `Row` | takes a share of the space left along the flow, in proportion to `n` (1 when bare); an empty `<Column grow />` is a spacer |
| `padding="step"` | any of the types above | space inside the element's edge, in the same steps |
| `minWidth="nem"`, `maxWidth="nem"` | any of the types above | bounds on the element's width, in `em` of the reader's body text (`maxWidth="40em"`) |
| `style="role"` | any of the types above | a named role, such as `heading`, `secondary`, `card` or `tag`; the client's theme decides how a role looks, and draws a role it doesn't know as none |

The client's theme decides how large each step is, so a view looks right on a phone, a
desktop and a dense or roomy theme, and widths in `em` scale with the reader's text size.
They say what a layout should do, not how to compute it: a client may lay them out with
stacks, flexbox or anything that gives the same result. A view can't name a layout
algorithm, place an element at a position, write constraints between elements or give a
color or font size. Grids and overlapping layouts are not in the language; a new layout is
a new element type from a client plugin
([Apps 014](../../plans/later/apps-014-client-plugins.md)).

## 10. An example

A whole view, using rules, expansion and drawn views:

```
// Profile.beetle
import data/schema.beetle
import parts/cards.beetle

rule curatedBy(l: List, person: Person):
  l.owner == person
rule curatedBy(l: List, person: Person):
  person in l.contributors.person

view(id):
  <Column spacing="large" for={person in Person} where={person.id == id}
    fallback={<Text style="heading">Profile not found</Text>}>
    <Text style="heading">{person.name}</Text>
    <Text style="secondary">@{person.handle}</Text>

    <Text style="heading">Practices</Text>
    <Row spacing="medium">
      <PracticeCard p={p}
        for={p in Practice} where={person in p.authors}
        orderBy={p.name} />
    </Row>

    <Text style="heading">Lists featuring their practices</Text>
    <Row spacing="medium">
      <ListCard l={l} for={l in List} where={person in l.items.practice.authors} />
    </Row>

    <Text style="heading">Lists they curate</Text>
    <Row spacing="medium">
      <ListCard l={l} for={l in List} where={curatedBy(l, person)} orderBy={l.name} />
    </Row>

    <Text style="heading">Collaborators</Text>
    <Row spacing="small">
      <Image person={other}
        for={p in Practice, other in p.authors} where={person in p.authors, other != person}
        orderBy={other.name} />
    </Row>
  </Column>
```

## 11. Handles and code versions

Overstory adds no application object, application identifier, entry component, route table, or location language. An app is an Overstory tree holding ordinary pages, `.beetle` files and typed nodes ([Beetle §2](2.2-beetle.md#2-beetle-files)). A host that supports execution serves a view at its file's own address.

The tree holding an app's files is identified by its existing `TreeID`; Overstory adds no application-ID
or script-ID namespace. `(TreeID, logical path, name)` identifies a named **handle**:
- a `.beetle` file's unnamed view, by its file's path and an empty name;
- a schema's unnamed view, by its `schema.beetle` path and an empty name;
- a named view, by its file's path and the view's name;
- a view block with no name, by the page's path and `#n`, its position among the page's
  unnamed views counting from 1, which only the page's own presentation uses;
- a mutation, by its file's path and its name.

A file's **code version** is the SHA-256 over the paths and text of the files and
schema files it uses, transitively, in path order, and is the version of each of its
handles. A `.beetle` file's text is its bytes; a page's is the text of its view blocks in
order, each without its fences and ended by a newline, so editing a page's prose changes no
code version. Each file contributes its path, a NUL, its text and a NUL. Moving a file or renaming a
declaration creates a different handle, just as moving any other node changes its URL;
changing a file a handle uses changes its version.

For each handle, checking exposes its parameters and their types, its code
version, the tables and paths it reads and writes, and public result metadata,
without disclosing source a caller may not read.

| Token | Identifies | Minted by | Survives |
|---|---|---|---|
| handle | one view or mutation, as `(TreeID, logical path, name)` | the author | code changes; not a move or a rename |
| code version | one checked file and everything it uses | hashing | moving the tree; prose edits in a page; not a change to any file it uses |
| schema fingerprint | one schema's data layer ([Beetle tables §5.3](2.3-beetle-tables.md#53-fingerprints)) | hashing the checked data layer | storage and code changes; not a data-layer change |

Adding a view does not publish it, run it, or grant it access: a host runs
views and mutations only for trees whose hosting it has enabled. It may check
eagerly or on demand, but a request uses one coherent code version of the addressed view and all of its handles,
and a file that fails checking never replaces the last usable version.

A reviewed manifest of what checked code needs, and static baking of reads,
are not yet specified
([Apps 010](../../plans/later/apps-010-activation-and-lending.md)).

## 12. Evaluating views on a host

A host that runs apps evaluates [Beetle](2.2-beetle.md) views and streams their results. A view
derives a current, permissioned value without exposing raw stores; it is not
accepted-tree synchronization.

```text
QUERY /.overstory/trees/{SourceTreeID}/views
Content-Type: application/json
Accept: text/event-stream
```

The request names every view a client currently shows from one source
tree. A server without an app runtime, or without hosting enabled for the
source tree, returns `422 unsupported-operation`.

```ts
/**
 * Names a view or a mutation: a name in a file in a tree (Beetle §6). `path` is the
 * logical path of a `.beetle` file's node, of a page, or of a collection's
 * `schema.beetle`, and `name` is empty for a file's unnamed view, a view's or mutation's
 * declared name, or `#n` for a page's unnamed view. `version` is the file's
 * code version (Beetle §6).
 */
type HandleRef = {
  tree: TreeID;
  path: LogicalPath;
  name: string;
  version: Hash;
};

type ViewsRequest = {
  views: Array<{
    id: string;
    handle: HandleRef;
    input: unknown;
    /**
     * What to answer (§4.1). `rows`: the plan's authorized rows, for a client
     * that evaluates the view. `tree`: the view tree, evaluated by the host.
     * Defaults to `rows`. Ignored for a data view, whose answer is its JSON.
     */
    form?: "rows" | "tree";
    knownOutputHash?: Hash;
  }>;
};

/**
 * Annotations on a `rows` answer, parallel to its JSON.
 * `row` is set on an object holding one row (its table, as `model`, and key).
 * `type` is set on a field's value (that field's type, as in Beetle §2.1). `fields` and `items` describe an object's members and an
 * array's elements.
 */
type ResultShape = {
  row?: { model: LogicalPath; key: string };
  type?: string;
  fields?: Record<string, ResultShape>;
  items?: ResultShape[];
};
```

Every handle's `tree` must equal the route `SourceTreeID`. The `views` array
is nonempty and its IDs are nonempty and unique within this request. The host
verifies each handle's code version, its input against the view's declared
types, the user context, effective access, and the schema fingerprints the
view's tables were bound to. A request carries no state ([§6](#6-state)). The request and events are independent of whether those nodes are
expanded files, row files, or SQLite. A
`knownOutputHash` permits omission of unchanged bytes only after fresh
authorization and reevaluation; it is neither
authorization nor evidence of current state. Output hashes are SHA-256 of the
canonical CBOR encoding of the complete public result.

A view's live dependencies are conservative: an ordinary read of a table's rows
depends on its resolved parent's membership and schema, the sampled child
identities and model hashes, and every field used by a condition or drawn.
Narrower dependencies are an optimization, and missing precision never skips a
reevaluation.

The UTF-8 SSE response has these semantic events:

```ts
type PublicQueryError = {
  code: string;
  message: string;
  retryable: boolean;
};

type ViewEvent =
  | {
      type: "result";
      id: string;
      outputHash: Hash;
      value: unknown;
      /** Field types and row identity for a `rows` answer (§4.1). */
      shape?: ResultShape;
      error?: never;
    }
  | {
      type: "result";
      id: string;
      error: PublicQueryError;
      outputHash?: never;
      value?: never;
    }
  | {
      type: "ready";
      views: Array<{
        id: string;
        outputHash?: Hash;
      }>;
    }
  | {
      type: "reload";
      reason: "source-changed" | "access-changed";
    };
```

The SSE `event` field supplies `type`; JSON `data` supplies the remaining
members. Each `result` is a complete authorized replacement for one view, not
a raw driver event or patch. `ready` is sent only after every view has
established a race-free snapshot-then-follow boundary. Before `ready`, changed
hashes produce complete `result` values and an unchanged retained value may be
confirmed by its hash in `ready`. Identical output hashes produce no payload.
The observation listener is active before sampling. Events racing evaluation
are checked against both the former and newly sampled dependencies; a relevant
event forces another complete evaluation before that result is published. This
is the no-gap guarantee. It does not require a retained view-event replay log.

`QUERY` has the safe and idempotent semantics defined by
[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008.html). Evaluating or
subscribing to a view never performs a mutation. The response is
user/access dependent and long-lived, so it carries `Cache-Control: no-store`;
automatic retry still reauthorizes and reestablishes current state rather than
reusing a cached body.

The response lifetime is the subscription lifetime. There is no durable
execution ID, acknowledgement, SSE replay cursor, or resumable server-side
subscription. Reconnection repeats and reauthorizes the complete `QUERY`. When
the set of views shown or their inputs change, the client opens a complete
replacement request and retains the old response only until the replacement
sends `ready`. Source or access changes send `reload` when possible and close.
Listener loss, backing uncertainty, process restart, or irrecoverable
backpressure closes rather than publishing a result known to be stale; hosts
may coalesce intermediate complete states.

### 12.1 Answer forms

The host loads one coherent code version of the named view and answers a UI
view in one of two forms, and a data view
([§8](#8-data-views)) with its JSON, kept current through the same
stream:
- **Rows**: the plan's authorized rows,
  annotated with field types and row identity, for a client that evaluates the
  view itself. The client evaluates the conditions that read state
  ([§6](#6-state)) and draws, so state changes redraw without a round trip.
- **Tree**: the view tree, evaluated by the host with the state's initial values,
  for a client that draws but doesn't evaluate. Such a client can't change state.

A browser `GET` of the view's address ([§13](#13-view-addresses))
gets a third form, **HTML**: the view tree rendered with the state's initial
values, with only what it draws embedded, its input taken from the query string.

A client holding a placed tree may evaluate a view against its local copy instead.

### 12.2 Plans and live dependencies

- **A plan is deterministic.** A view's result depends only on the nodes it reads, its
  validated input and the user context, and means the same whichever representation
  holds the rows: a host may run it as SQL, through indexes or by walking the tree.
  Matches without `orderBy` come in canonical stable-key order.
- **Baseline only.** Paths, `count`, `sum`, `min`, `max`, `exists`, ordering, grouping by
  a value and limits are baseline ([Beetle §4](2.2-beetle.md#4-expressions-and-built-ins)).
  Other aggregates, pagination and unbounded traversal are not yet specified
  ([deferred 6](README.md#deferred)), and a view that needs them fails at checking rather
  than loading a whole tree.
- **Bindings are checked first.** Before a plan reads or a mutation begins, the host
  checks each table's binding `(TreeID, logical path, schema fingerprint)` against the
  tree. A binding that no longer resolves the same way makes the handle inactive; it is
  never redirected to a same-named typed node.
- **Live results never miss a change.** A host reruns a view whenever something it read
  may have changed: a node, a field, a typed node's rows or schema, a mounted root, or
  a profile or access fact. That includes a row added or removed while the view was being
  read. Watching more narrowly is an optimization and never changes a result.
- **Where a plan runs.** A server holding the nodes may run a plan if it enforces the same
  validation, access and versions, and a read-only placement may serve a plan's last
  complete result offline. Cross-server plan routing is not yet specified
  ([deferred 2](README.md#deferred)).

## 13. View addresses

A view's address is its file's address, extension and all. Visited there, `List.beetle`
draws its unnamed view as a page of its own: `GET {canonical URL}/List.beetle?id=…` serves
it ([§12.1](#121-answer-forms)), and a link to it opens it
([locators §3](1.4-locators.md#3-parsing-and-canonicalization)). A page draws a view
only through a view block ([§5](#5-view-blocks-in-pages)); a link to a view, even
alone on its own line, is an ordinary link.

A named view is addressed by its file with a `view` parameter naming it,
`Notes?view=Drafts`, `parts/cards.beetle?view=PracticeCard` or
`data/schema.beetle?view=ByOwner`. A schema's unnamed view is addressed by its typed node's
folder ([Beetle tables §5](2.3-beetle-tables.md#5-a-typed-nodes-schema)), and a view block with no name
has no address of its own. There is no default: a page without `view` is the page, a
`.beetle` file without `view` is its unnamed view, a schema file without `view` is the
schema's source, and a name that isn't declared there is not found. A `.beetle` file with
no unnamed view draws nothing when visited.

Links resolve as this chapter defines. A same-tree host may
intercept an ordinary link for client navigation, but the link must remain
correct as an ordinary HTTP navigation with JavaScript absent. Back, forward,
reload, open-in-new-tab, and copying the URL use browser semantics rather than
a parallel application history.

The query string is the view's input. A name that occurs once becomes its
string, a repeated name an array in order, and an omitted name is absent; the
view's typed parameters (Beetle §3) convert and validate the result
before any data access, as for a form ([§7](#7-actions-forms-and-events)).
Apart from `view` naming a view, there is no reserved parameter, generated
link constructor, or global list of allowed query keys. Unknown parameters are
ignored.

The optional path-attached `;overstory-key=...` identity suffix is consumed
before the view is resolved and never reaches its input. It can therefore heal
or redirect a renamed view without taking a query parameter away from it.
Healing preserves the complete query string unchanged.

Fragments retain ordinary document-fragment behavior. Node identity, server
rendering, authorization, metadata, and initial reads cannot depend on fragment
data unavailable to the server.
