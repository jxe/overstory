# Beetle

Beetle has no general-purpose code. A typed node's tables are declarations; a view's reads are plans a host finds in the file alone, and its markup is a view tree; a mutation is a set of facts that hold once it has run. Interpreting a file never executes code: a conforming implementation parses and checks it under the limits of [§5](#5-limits-and-diagnostics) and derives everything else from the checked result. Extending the data with code of a general-purpose language is not yet specified ([client plugins](../../plans/later/apps-014-client-plugins.md), [runners](../../plans/later/apps-017-data-runners.md)).

Beetle declares data and the views and changes over it. A typed node's `schema.beetle` can hold
all three:

```
// practices/schema.beetle
main table Practice:
  name:  Text
  about: Markdown?
  likes: Int = 0

mutation like(p: Practice):
  p.likes = p.likes + 1

view():
  <Column>
    <Row for={p in Practice} orderBy={p.likes desc}>
      <Text>{p.name}</Text>
      <Button action={like(p: p)}>👍 {p.likes}</Button>
    </Row>
  </Column>
```

`Practice` is a **table**: its rows are the typed node's children, `/practices/walking`
([Beetle tables](2.3-beetle-tables.md)). The unnamed **view** is what the typed node shows at `/practices`. Its
`for` is a read, a plan the host finds in the file without running anything, and the `Row`
appears once per practice ([views](3.1-views.md)). `like` is a **mutation**: its lines are facts
that hold once it has run, here that the practice has one more like ([mutations](3.2-mutations.md)).
Views and mutations may also sit in their own `.beetle` files and in view blocks in pages
([§2](#2-beetle-files), [views §5](3.1-views.md#5-view-blocks-in-pages)).

The rest of this chapter defines tables (§2), views (§3), mutations (§4), and what a
typed node's `schema.beetle` adds: its views and how its tables are stored
(§5). §6 names handles and code versions, §7 sets limits and §8 summarizes the grammar.

## 1. Syntax

A `.beetle` file is UTF-8 text without a byte-order mark. A comment runs from `//` to the
end of the line. Space, tab and carriage return separate tokens, and a line feed ends a
line.

**Indentation groups.** A declaration's header ends with `:`, which always ends its line,
and its body is the lines below it indented further, by spaces. A body ends at the first
line indented no further than its header. Inside parentheses, lists `[ … ]` and record
values `{ field: value, … }`, line feeds and indentation are ignored and items are
separated by commas. Braces hold only record values here, and `{expression}` in a view's
markup ([views §1](3.1-views.md#1-elements)).

An identifier is `[A-Za-z_][A-Za-z0-9_]*`. A number is an optional `-`, decimal digits,
and an optional fraction. A string is double-quoted on one line, with `\"`, `\\`, `\n`
and `\t` escapes.

The words `main`, `table`, `my`, `session`, `enum`, `re`, `seed`, `ordered`, `unique`,
`path`, `as`, `body`, `title` and `index`, and the words the rest of this chapter uses, are keywords
only where they are placed, so a field or table may still be named `id`, `seed` or
`path`.

## 2. `.beetle` files

Views are written in `.beetle` files, in view blocks in pages ([views §5](3.1-views.md#5-view-blocks-in-pages)),
and in a typed node's `schema.beetle` ([Beetle tables §5](2.3-beetle-tables.md#5-a-typed-nodes-schema)). To the language each
is a file, and any file may declare views, rules, mutations and state tables
([views §6](3.1-views.md#6-state)); a typed node's data tables are declared only in its `schema.beetle`.

A `.beetle` file is a file, addressed by its name with its extension
([data model §8](1.1-data-model.md#8-mapping-files-and-directories-to-nodes)), and its
unnamed view is what it draws when visited. A typed node's `schema.beetle` draws its
source instead, and its unnamed view is the typed node's
([Beetle tables §5](2.3-beetle-tables.md#5-a-typed-nodes-schema)). `Drafts.beetle` is a
view, and `Drafts.beetle?status=review` shows the essays under review:

```
// Drafts.beetle. Essay is a table of the nearest schema.beetle.
view(status):
  <Column>
    <Row for={e in Essay} where={e.status == (status ?? "draft")} orderBy={e.date desc}>
      <Text>{e.title}</Text>
      <Text style="secondary">{e.date}</Text>
    </Row>
  </Column>
```

A file is a sequence of declarations, in any order, written as [§1](#1-syntax) says:

| Declaration | Declares |
|---|---|
| `import path`, `from path import names` | another file, `.beetle` or page, whose names this file imports ([§3](#3-using-other-files-and-views)) |
| `view(params):` and an element | an unnamed view ([views](3.1-views.md)): a `.beetle` file's view, at most one per file, or a view drawn where its block sits |
| `view Name(params):` and an element | a named view, addressable and drawn as an element `<Name …/>` ([§3](#3-using-other-files-and-views)) |
| `rule name(params):` and conditions | a rule ([views §3](3.1-views.md#3-conditions-and-rules)) |
| `mutation name(params):` and facts | a mutation ([mutations](3.2-mutations.md)) |
| `my table`, `session table`, `enum` | a state table ([views §6](3.1-views.md#6-state)), or an enum ([Beetle tables §2](2.3-beetle-tables.md#2-enums)) |
| `table`, `main table`, connections, `re` | a typed node's data tables, only in its `schema.beetle` ([Beetle tables](2.3-beetle-tables.md)) |

Beetle is versioned with this specification. The tree's shape never depends on code: a
`.beetle` file is a file whether or not it checks, and a file of any other extension,
`.tsx` included, reads as an ordinary file. Structured editors that cannot preserve a
`.beetle` file or a view block exactly must use a raw or code-capable mode. They never
rewrite it as ordinary Markdown.

## 3. Using other files and views

A file imports what other files declare in one of two ways, the path first:

```
import List.beetle                                           // all of its names
from ui/cards.beetle import PracticeCard, Card as PlainCard  // only these
from views/reading-room.beetle import view as ReadingRoom    // its unnamed view
```

- **`import path`** makes the file's tables, named views, rules and mutations
  available by their own names, and a `.beetle` file's unnamed view available as an element
  named after the file's node, `List` for `List.beetle`.
- **`from path import names`** makes only the listed names available. `Name as Other` makes
  one available as `Other`, and `view as Name` names a `.beetle` file's unnamed view, which a
  file whose node name isn't a name, such as `reading-room.beetle`, needs before its view
  can be drawn. A listed name the file doesn't declare is a check error, so a library
  that renames something fails where it is used. A `from` import is the form for libraries.

Names a file declares shadow the names it imports. Two imports making the same name
available is a check error at the second; the fix is a `from` import that leaves one
out or renames it. Nothing is available without an import, except the schema below.

The path names a `.beetle` file, a page or a typed node's `schema.beetle` as a Markdown link
would, relative to the importing file, and is written bare, or quoted when it holds a space; another tree's file is named by an absolute Overstory
locator and resolves to one immutable code version for one build or execution. A file
can't import itself, directly or through others. Everything a file declares can be imported;
there are no export lists.

A file binds the typed node schema of its folder or nearest ancestor that has one without
an import, and `import data/schema.beetle` binds another. Checking resolves each table, field
and path against the schemas and state tables a file binds, and fails on a name it can't
resolve. Schema information and explicit relationship declarations are mapped to
canonical tree-rooted typed node paths, so files remain portable across placements. A
change to a typed node's data layer changes its schema fingerprint
([Beetle tables §5.3](2.3-beetle-tables.md#53-fingerprints)) and invalidates dependent checked handles; a storage change
alone invalidates none.

A **named view** can be drawn as an element whose type is its name, with its
parameters as attributes. This one, from `parts/cards.beetle`, is also addressable as
`parts/cards?view=PracticeCard&p=…`:

```
view PracticeCard(p: Practice):
  <Column style="card">
    <Link style="heading" to="Practice?id={p.id}">{p.name}</Link>
    <Row spacing={4}>
      <Text style="secondary">by</Text>
      <Image person={a} for={a in p.authors} orderBy={a.name} />
    </Row>
    <Markdown source={p.about} lines={6} />
  </Column>
```

A drawn view reads only through its own `for`, `where` and paths, which join the plan
of each view that draws it. Drawing another view, or using a file from another tree,
acquires no grants ([access control §4.3](5.2-access-control.md#43-authority-and-consent)). A link to a view
is its address, written like any link and resolved from the file that holds it:
`to="Practice?id={p.id}"`.

## 4. Expressions and built-ins

Expressions are literals, names, paths, calls and operators. Literals are text in double
quotes (which may hold `{expression}`), numbers, `true`, `false`, `null`, lists `[a, b]`,
records `{ name: value }`, and durations (`16ms`, `1s`, `5m`, `2h`, `7d`). An enum value
is written by name (`Public`). A path through a many-valued field is a set of distinct
values ([views §2](3.1-views.md#2-reading-rows)).

| Operators, by precedence | Means |
|---|---|
| `.` | follow a field |
| `not`, unary `-` | negation |
| `*`, `/` | arithmetic |
| `+`, `-` | arithmetic; `+` joins text; a date plus or minus a duration, and a date minus a date; on a set, `+ x` adds a member and `- x` removes one |
| `==`, `!=`, `<`, `<=`, `>`, `>=` | comparison; comparing a set with `==` is a check error |
| `x in S` (`x ∈ S`), `S excludes x` (`x ∉ S`) | membership in a set or list, or containment of text, and its negation |
| `and` | both |
| `or` | either |
| `a ?? b` | `a`, or `b` when `a` is `null` |
| `c ? a : b` | choice |

Nulls have no third truth value: `null == null` is true, any other comparison with `null`
is false, and a path through a `null` is `null`.

Built-in functions are pure: `count(path)`, `count(name in source where …)`,
`exists(name in source where …)`, `sum(path)`, `min(path)`, `max(path)`, `lower(text)`,
`upper(text)`, `trim(text)`, `length(text)`, and `set` in actions. `me`, `community`,
`page`, and, in mutations and defaults, `now` and `today` are built-in names. A name a
file declares may not reuse a built-in name.

## 5. Limits and diagnostics

| Limit | Value |
|---|---|
| Source bytes | 1,048,576 |
| Tokens | 65,536 |
| Nesting depth of values | 32 |

Each limit applies to one file, and exceeding one rejects the file.

A rejected file reports diagnostics with a stable code, a file and a 1-based
line and column. The [`collection-schemas.json`](conformance/collection-schemas.json)
vectors bind the codes they list; messages are not normative.

## 6. Grammar

An informal summary of Beetle's syntax; the sections above define what each form means.
A `:` ending a header line groups the indented lines below it as its body.

```text
file        = { import | table | enum | re | view | rule | mutation }
import      = "import" path | "from" path "import" pick { "," pick }
path        = string | a run of characters up to a space
pick        = ( name | "view" ) [ "as" name ]

table       = [ "main" | "connection" | "my" | "session" ] "table" Name
              [ "(" name { "," name } ")" ] [ as ] ":" { field | index | seed } (§2.1, §5.2)
field       = name ":" { modifier } Type [ "?" | "[]" ] [ other ] [ "=" default ] { storage }
other       = "<->" [ "ordered" ] name [ "?" | "[]" ]                     (§2.3)
enum        = "enum" Name ":" { field } { value }                (§2.2)
value       = ( Name | string ) [ record ] [ as ]
seed        = "seed:" { value }
re          = "re" Name [ as ] ":" { ( name | Name ) { storage } | index }
storage     = as | "as" "array" | "body" | "title"                      (Beetle tables §5.1)
as          = "as" string
index       = "index" name { "," name }

view        = "view" [ Name ] params ( ":" { stateLine | eventLine } element | record )
record      = "{" [ entry { ( "," | newline ) entry } ] "}"                (§3.12)
entry       = name | name ":" ( expression [ record ] | { attribute } record )
rule        = "rule" name params ":" { expression }
mutation    = "mutation" name params [ "for" Name "." op ] ":" { line }
params      = "(" [ param { "," param } ] ")"
param       = name [ ":" Type [ "?" | "[]" ] ]
stateLine   = ( "state" | "keep" ) name "=" expression
eventLine   = ( "on" "key" string | "every" duration ) "→" action
element     = "<" Type { attribute } ( "/>" | ">" { element | text } "</" Type ">" )
attribute   = name [ "=" ( string | "{" expression "}" ) ]                (in elements)
action      = call                                                      (§3.10)
line        = [ "not" ] Name "(" args ")" | "let" name "=" Name "(" args ")"
            | path "=" expression | call | code [ string ]
            | "if" expression ":" { line }
            | "for" name "in" expression [ "where" expression ] ":" { line }   (§4)
code        = "unauthorized" | "forbidden" | "missing" | "invalid" | "conflict"
expression  = literal | name | path | call | operator form              (§3.4)
```
