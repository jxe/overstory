# Beetle tables

A typed node's `schema.beetle` declares its data tables and how they connect:

```
main table Game as "games":
  name:        Text title
  status:      Status <-> games[]
  description: Markdown? body
  tags:        Text[]
  authors:     Person[] <-> games[] as array
  first:       Date = today

  index status, created

table List:
  name:  Text
  games: ordered Game[] <-> lists[] as array

enum Status:
  color: Text

  Draft       { color: "#9aa0aa" }
  Playtested  { color: "#bd861a" }
```

The words `as`, `body` and `title` at the end of a line, and `index` lines, say how a
placement stores a table; they never change the rows
([§5.1](#51-data-and-storage)).

## 1. Tables and fields

`table Name:` declares a table, whose body is its fields, and `main table Name:` the
typed node's main table. A table or enum name is unique, and `Person` and the value type
names are reserved.

`main table Practice:` makes Practice the typed node's main table: its rows are the
typed node's own children (`/practices/walking`). Every other table with data rows
is a child of the folder named after the table, holding that table's rows
(`/practices/Tag/t1`), so adding a table never moves the main table's rows. A schema has
at most one `main` table, and an enum or connection table can't be one. A main row whose
name equals another table's name is invalid.

A field is `name: [modifiers] Type [= default]`, written as a call gives it. The type is a value type or a table name,
optionally followed by `?` (at most one value) or `[]` (any number). Modifiers go between
the name and the type:

| Modifier | On | Meaning |
|---|---|---|
| `ordered` | a many-valued field or connection end | its members are a sequence; merges as one |
| `unique` | a single value field | no two rows share its value |
| `path` | one required `Text` field | its value is the row's name in the tree; otherwise the key names it |

A **default** after `=` is the value a mutation writes when it creates a row without
giving that field ([mutations §1](3.2-mutations.md#1-facts)). It is a
literal, an enum value, `me`, `now` or `today`, evaluated when the row is created, so a
field written only on creation (`first Date = today`) needs no mutation to say so. A
required field with no default must be given when a row is created.

The value types are:

| Type | Values |
|---|---|
| `Text` | one line of text |
| `Markdown` | paragraphs of text; merges by lines |
| `Int` | an integer within ±(2^53 − 1) |
| `Number` | a finite number |
| `Bool` | `true` or `false` |
| `Date` | an ISO 8601 date or date-time |

A value array (`tags Text[]`) is held on the row. A field whose type is a table is a
cross-reference to a connection ([§3](#3-connections)); it must agree with the connection
in target and arity.

`Person` is a built-in table: Overstory profiles, referenced by profile id. It has
no rows in any typed node. A `Person` value is a profile id (the profile's
TreeID: `tr_` and lowercase base32, `a`–`z` and `2`–`7`), or a
*placeholder* `contact:<key>` for someone with no profile yet, where `<key>`
(1 to 128 of `A`–`Z`, `a`–`z`, `0`–`9`, `_` and `-`) names a row of the
People rows of the viewer's directory. Any other text beginning `contact:` is
invalid. A reader shows a placeholder by the name its directory has for that
row, or by its key when it can't resolve it, and never drops it. When the
person gets a profile, their placeholders are rewritten to the profile id.

Every row has the implicit fields `id`, `created` and `modified`, which a table can't
declare and a mutation can't write. `created` and `modified` are date-times that only
accepted changes set ([typed nodes §2](2.1-typed-nodes.md#2-children-and-values)).

## 2. Enums

An enum is a table whose rows are written in the schema: its values, one per line.

```
enum Status:
  Draft
  Playtested
```

A reference to an enum is the value's name, written unquoted in expressions
(`g.status == Draft`), and an enum has no stored table. A value name that isn't an
identifier is a string (`"Current focus"`).

An enum whose values carry data declares its fields first, then its values, each with a
record of its fields' values:

```
enum Genre:
  blurb: Text

  Puzzle    { blurb: "Think it through" }
  Strategy  { blurb: "Plan ahead" }
```

An enum can't be a connection table, and its values can't be changed by editing data.
When people need to add values, the enum becomes a `table` with a `seed:` block, written
in the same form: seed rows are data, inserted when their `id` (the value's name) is
missing and never overwritten, so stored references stay valid. A seeded table needs a
`name Text` field.

## 3. Connections

A field whose type is a table is a **connection**, and after `<->` it names the field the
other table gains: in `List`, `owner: Person <-> ownedLists[]` gives each list an `owner`
and each person the lists they own. A connection is written once, as a field of either of
its tables (in the table or enum, when the other side is `Person` or an enum); the other
side's field exists without being written. `[]` makes a side many and `?` optional, and
`ordered` before a side's type or name makes its members a sequence (`games: ordered
Game[] <-> lists[]`); at most one side is ordered, and no two connections give one table
the same field. The connection's arity is that of its sides: many on both is n:m, on one is
1:n, on neither is 1:1.

`as array` after the other side keeps this field, in data files, as an array on its
table's rows instead of a table of its own ([§5.2](#52-layout)). Only an n:m connection
can, and only on one side; it never changes the rows.

A table may also list the other side of a connection written elsewhere as a plain field,
`lists: List[]` in `Game`, to place it among its own fields. It must agree with the
connection's arity and has no `ordered` or storage of its own.

`connection table Name:` declares a **connection table**. Its connection fields are its
ends, each one row on its own side, and it may carry fields of its own:

```
connection table Item:
  list:     List <-> ordered items[]
  practice: Practice <-> items[]
```

An item connects one list and one practice, and a list's `items` are its items in order.
`as array` on one end keeps the table's rows, in data files, on that end's rows.

## 4. Keys

A table's rows are keyed by `id`, except:

- a connection table is keyed by its ends' fields, so it holds at most one row
  per combination;
- a key in the table's header, `table Tag (list, id):`, keys rows by the named
  single-valued fields (`id` included), here an id unique within its list;
  `table Review (id):` gives a connection table its own `id`;
- an enum's rows are keyed by their names.

## 5. A typed node's schema

A typed node's `schema.beetle` declares its data tables (§1 to §4), and may declare
views, rules and mutations beside them. It is the typed node's `schema`, a file object rather than a child
([data model §5](1.1-data-model.md#5-objects)), and not a page ([typed nodes](2.1-typed-nodes.md)), and what it declares is used with
`import data/schema.beetle` like any file's.

- **Its unnamed view is the typed node's view.** `view():` in a schema is what the
  typed node shows when it is visited, at the folder's own address
  (`/practices`), unless the folder's page has content. A folder with a page is
  that page, which draws the typed node's view with a view block like any other
  (`from schema.beetle import view as Practices`).
- **Its named views are other ways to show the typed node.** They are addressed by the
  schema file's path, `data/schema.beetle?view=ByOwner`
  ([views §13](3.1-views.md#13-view-addresses)), and a client may offer them as
  alternatives to the typed node's view.
- **A typed node with no views** shows a plain `Rows` list of its main table, or of its
  first table with rows, and a client may offer the same list grouped by each enum,
  connection or `Person` field.

```
view():
  <Column>
    <Text style="heading">Lists</Text>
    <ByOwner />
  </Column>

view ByOwner():
  <Rows for={l in List} group={l.owner} orderBy={l.modified desc}>
    <Text>{l.name}</Text>
  </Rows>
```

A view in a schema is a view like any other: a host serves it through
[views §12](3.1-views.md#12-evaluating-views-on-a-host) with the same plan,
authority, live behavior and result forms, and a client draws it wherever a view can
appear.

### 5.1 Data and storage

How a placement stores a typed node's tables is set by storage words, in the schema and in
the placement's own mapping, and determines its layout. None of it changes the rows a tree
holds.

A schema says two kinds of thing:

| Layer | Written as | Says | Shared by |
|---|---|---|---|
| data | declarations and keywords | tables, fields, types, keys, connections, enum values | every placement; it is what the tree holds ([§5.3](#53-fingerprints)) |
| storage | `as`, `body` and `title` at the end of a line, and `index` lines | how a placement stores a table: folding, table and column names, indexes, a row's body and title | defaults every placement starts from, which a placement's own mapping may override |

Storage words come last on the line of what they apply to, after any default:

| Written | On | Meaning |
|---|---|---|
| `as "name"` | a table's header (`main table Game as "games":`) | the stored table's name |
| `as "name"` | a value field, or the end that stores a connection | the stored column's name |
| `as "text"` | an enum value (`Draft as "draft"`) | the text a store holds for that value |
| `as array` | one end of an n:m connection, or of a connection table | keeps the connection, in data files, as an array on that end's rows ([§5.2](#52-layout)) |
| `body`, `title` | one `Markdown` field; one `Text` field | in Markdown row files, the field written as the body, and the one written as the page title |
| `index field, ...` | a line in a table's body, any number of times | databases index those single-valued fields (`id`, `created` and `modified` included) in that order |

Without `body` and `title`, a Markdown row file's body is the `Markdown`
field named `content` and its title the `Text` field named `title`, when the
table has them. By convention, which `beetle fmt` applies, `index` lines come last in a
body, after a blank line.

A table or enum is declared once. `re Name:` adds storage to a table or enum declared
elsewhere in `schema.beetle`, or from a placement's storage mapping. Its header may carry
the table's `as "name"` (`re Game as "games":`), and its lines re-mention fields by bare
name (`title as "name"`) and an enum's values by name (`Draft as "draft"`), or are `index`
lines. A `re` block never declares fields, types or values.

**Precedence.** Storage is derived from the tables, then from storage words in the tree's
schema, then from the placement's own mapping: `re` blocks that the placement keeps
outside the tree, where its implementation chooses
([placements on disk §6](6.2-placements-on-disk.md#6-local-placements)). A mapping is
needed only where a store's names differ, such as an existing database the schema didn't
create. Setting one storage word twice at one level of precedence is an error.

### 5.2 Layout

The checked schema and its storage determine the tables, columns and keys a
placement's store holds: its *layout*. A layout is a projection of the logical
form ([typed nodes §2](2.1-typed-nodes.md#2-children-and-values)), so the
two layouts below hold the same rows and changing one never changes data.

- A table with data rows is stored as a table named after it, or its `as` name.
  `Person` and enums have none: a reference to a person is a profile id (or a
  `contact:` placeholder), and a reference to an enum is the value's name (or its
  `as` text).
- A stored table's primary key is its table's key. A key field that refers to another
  table expands to that table's key columns: one column named after the field
  when the target's key has one column, otherwise `field_key` for each.
- A 1:1 or 1:n connection is a column (or columns) on its single side,
  nullable when that end is optional. An n:m connection is a join table named
  `Table_field` after its first end, keyed by both ends.
- A connection table is stored keyed by its ends, unless one end is `as array`.
- An `ordered` many end adds a `field_position` number where the connection is
  stored. Positions are the store's own: a placement writes and renumbers
  them freely, and only their order is data.
- Every stored table has `created` and `modified` columns.
- Database tables index each reference that doesn't lead the primary key,
  profile ids included, and each `index` line. An index whose columns begin
  another index is left out. Indexes never change what a database holds, so
  implementing a schema doesn't depend on them.
- **Data files** follow the same tables, except that an n:m connection with a
  `as array` side is an array, on that side's rows, of the other side's keys, in
  order when the end is `ordered`. Databases always use a join table.

Two fields stored under one column name are an error. Setting up a database
from a layout creates only what is missing and inserts seed rows only when
missing; it never alters or drops anything.

A database implements a layout when every table and column exists with a
compatible type and nullability, keys and foreign keys match, and any extra
column is nullable or has a default. Extra tables are allowed.

Each connection end is also a named relationship from its table:
`List.owner` reaches one `Person`, `List.items` the `Item` rows of a list, and
`Practice.authors` the people through the join table. Views and mutations
read along these as paths ([views §2](3.1-views.md#2-reading-rows)).

### 5.3 Fingerprints

A typed node binds to its schema's **schema fingerprint**: the canonical CBOR hash
([data model §7](1.1-data-model.md#7-cbor-and-hashes)) of the checked data layer, with
tables, enums, fields, values and connections in UTF-8 order of name. Comments,
formatting, defaults, all storage, state tables, and the schema's views,
rules and mutations are left out. Changing only storage or the schema's
code therefore leaves every typed node's logical state and hash unchanged.

Storage has no fingerprint of its own.
