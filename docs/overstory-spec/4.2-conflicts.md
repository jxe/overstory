# Conflicts

When two changes can't both be applied, the host can still accept the update and keep
both sides as a decision in the accepted state, rather than rejecting one of them
([updates and merging §3.2](1.3-updates-and-merging.md#32-the-acceptance-procedure)).
This chapter is that accepted unresolved state: how a reader sees it, how a writer resolves
it, how editing continues around it, and the rules that settle it automatically.

## 1. Accepted unresolved state

`AcceptedUpdate.conflicted` and `RemoteTreeDescriptor.conflicted` signal that
an accepted state retains unresolved alternatives. The field is required; a descriptor and its accepted update MUST agree. This state is distinct
from a rejected update's structured `409 conflict` response. The selected `root`
remains an ordinary valid directory graph with no conflict markers or special
entries. An accepted change to unresolved state MUST receive a new update id
even when the predecessor root equals `root`; its transition may be empty.
Clients MUST durably advance accepted metadata in that case.

Clients without conflict-review support may continue ordinary synchronization
and MUST indicate unresolved state rather than reporting the tree as
conflict-free. How the host keeps, continues and resolves accepted decisions is
[§3](#3-explicit-resolution); how a client
keeps working around them is
[working trees §6](6.1-working-trees.md#6-accepted-conflicts-and-held-local-work).
A client ignores unknown optional response fields.

## 2. Reading conflicts

```text
GET /.overstory/trees/{TreeID}/conflicts?update={update}[&after={token}][&conflict={id}]
```

This lists the open decisions in one retained accepted state. `update` is
required and exact; `after` continues from a page token, and `conflict`
selects one decision instead (the two are exclusive). Each query field occurs
at most once. Every page is authorized afresh. An unknown or unreadable tree,
an unretained state and an unknown decision are `404`; a malformed or
mismatched page token is `400`. A token is bound to its tree, state and
position and grants nothing.

```ts
type DecisionPage = {
  tree: TreeID; update: string; root: Hash; conflicted: boolean;
  decisions: Decision[];
  next: string | null;
};
type Decision = {
  id: string;
  kind: string;
  affected: Ref[];
  selected: string;
  record?: { table: Name; key: string; field: Name | null };
  property?: Name;
  alternatives: Array<{
    id: string; revision: string;
    value: { text: string } | { file: Hash } | { directory: Hash } | { page: Hash }
         | { tree: TreeID } | { absent: true } | { value: JSONValue };
    placement?: EntryDestination;
    contributions: Array<{ change: string; operation: string | null }>;
  }>;
  dependencies: string[];
};
```

**Pages.** Every page repeats the requested `tree`, `update` and `root`;
`conflicted` describes the whole state. A complete traversal yields each
decision once, in a stable order, and stays at its state even if the tree
advances; `next: null` ends it, and a page that is not the last makes
progress. A read with `conflict` returns that one decision with
`next: null`. An empty page never means resolved. The protocol caps neither
decisions, alternatives, dependencies nor contributions; page size is a
transfer choice.

**Decisions.** A decision is complete on its page: all its alternatives and
dependencies. A dependency may name a decision on another page, which a
client fetches by `conflict` at the same update; before resolving several
decisions jointly it fetches the dependencies it needs, but ordinary sync
needs neither a full traversal nor that closure. `affected` uses the
references of [reading §4](1.2-reading.md#4-references-and-selectors), with a basis reference
read at the page's `update`; an absence can be addressed by its destination
parent. `selected` names the alternative the projection shows. Unknown kinds
may be shown as unavailable but authorize nothing new.

**Alternatives.** An alternative's `value` is exact text, a typed entry
(never guessed from bytes), a record or property value, or `absent`.
`placement` is the parent and name proposed for an entry value, and is
invalid for text or absence. `contributions` name the authored input, with a
null `operation` for a snapshot. Decision and alternative IDs are stable
across pages; a `revision` changes when the value, placement or
contributions do. Equal bytes never merge two alternatives. A mutation
addresses an alternative by an alternative reference with this page's
`update`. Entry-valued alternatives are read through the
[object route](1.2-reading.md#3-reading-an-object-at-a-time) by the hashes the page gives;
the host retains them as long as the state.

A `field` decision is a choice about one field of one record of a typed node
([updates and merging §3.6](1.3-updates-and-merging.md#36-merging-properties)):
`affected` names the typed node, and `record` the table, the record's
canonical stable key and the field, with `field: null` for whether the record
exists. A `property` decision is the same choice about one property of a
page, named by `property`. Their alternatives' values are `{ value }`
holding the field's or property's value, or `{ absent: true }` when it is
absent. A client resolves them with
property operations ([updates and merging §2.5](1.3-updates-and-merging.md#25-property-operations)).

Every decision can be resolved, and an alternative edited, with ordinary
operations and resolution declarations
([§3](#3-explicit-resolution)).
IDs and references use [reading §4](1.2-reading.md#4-references-and-selectors) syntax and are
unique within their scopes; a dependency never names its own decision, but
decisions may depend on each other in a cycle. An open decision has at least
two alternatives. Responses are private and never stored by shared caches.
The [read vectors](conformance/protocol-accepted-state.json) bind the
TypeScript and Swift models.

## 3. Explicit resolution

A consumer that requires resolved material checks that condition when it
consumes it; there is no resolved-only write mode.

```ts
type ResolutionDeclaration = {
  update: string;
  conflict: string;
  alternatives: string[];
};
```

A declaration in `resolves` explicitly endorses the candidate's resulting projection
for the named decision. It does not carry its own replacement language or clear an
arbitrary flag. The operations or snapshot describe the authored result; the
declaration supplies resolution intent and guards. For hidden material to become
the chosen result, the candidate must materialize it using the appropriate ordinary
operations. Editing a hidden alternative alone does not select it.

`update` identifies the exact reviewed accepted evidence. `alternatives` is the
complete nonempty set of reviewed alternative IDs, with no duplicates. The host
loads their revisions, contributions and dependencies at that state and compares the
relevant evidence with current. New or changed alternatives, affected locations,
projection choices or dependencies invalidate the review. Unrelated advancement need
not invalidate it when the host proves the guarded decision unchanged. `ifCurrent`
is available when the caller requires no accepted advancement at all.

There is no fixed protocol count limit on declarations or reviewed alternatives.
A conflict may appear only once. Array order is retained in request identity, but
all declarations take effect jointly, never sequentially. The host validates
that the candidate fully expresses each resolved choice and preserves all unnamed
open decisions. Ordinary saves, equal bytes and omission of hidden material never
resolve a decision implicitly.

Coupled decisions use one candidate with all required operations and declarations.
The host validates a coherent combined result against dependencies and model
constraints, then accepts everything atomically or rejects that candidate. Several
request elements are not a substitute: they can leave an accepted prefix. A dependency
does not force joint resolution if an individual choice leaves the other alternatives
meaningful and correctly attached. New concurrency affecting a resolved choice causes
rejection, not silent expansion of the person's resolution. Unrelated edits may merge.

Keeping the existing projection can use an empty trace (`trace: []`) plus guarded `resolves`.
It advances accepted identity even with an unchanged root. An automatic rule uses the
same resolution invariants with separately recorded authority authorship under [§4](#4-accepted-decisions-and-continued-editing).

## 4. Accepted decisions and continued editing

The host keeps three things apart: contributions, unresolved decisions, and
the projected file graph. The projection is always a valid ordinary graph with
no conflict markers; its correspondence to each decision's alternatives is
part of accepted state, and hidden alternatives and their objects stay
readable as long as the state is retained. Decision IDs are stable within a
tree. Alternatives keep their identity, revision and provenance, and equal
bytes, order or paths never identify or merge them. A decision may concern
content, existence, placement or attachment; dependencies constrain which
combinations are valid, without enumerating whole-document combinations.

An ordinary edit continues the alternative it is attributable to and leaves
the others, and the open decision, in place. Returning to base bytes or
matching another alternative is not resolution. Ambiguous attribution is kept
when it can be represented; invalid claims, missing evidence and exceeded
bounds fail.

An accepted unresolved result acknowledges work normally: it pauses no sync and
stops no later element of its request. The host owns attribution and resolution
on every write path, so a client needs no alternative map to keep editing
([§1](#1-accepted-unresolved-state)).

Inspection is authorized and scoped to accepted state. It supplies the
complete relevant identities, locations and dependencies without requiring
a full provenance graph. [§2](#2-reading-conflicts)
specifies text, whole-entry and placement inspection using the same reference
vocabulary.

## 5. Format-aware merge rules

A merge rule reads exact source, its structure or schema, provenance and open
decisions; a filename extension alone is not enough, since frontmatter and
embedded code may merge differently from prose. A rule justifies a resolved
result, names the remaining choices, or declines. It accounts for every
competing contribution, preserves unaffected bytes and identities, and
validates its result. Binary content needs an applicable rule, or
alternatives, never a text fallback.

A node's page, children and base merge independently: an edit to a page and a
change among the node's children never conflict with each other, and two
different bases for one page are a choice like any other value.

A rule that clears an existing decision is an automatic resolution: it records
the state and alternatives it considered, its own identity and revision, the
result with its provenance, and why. A human resolution records the reviewed
operation and alternatives instead. Either preserves independent decisions,
checks dependency guards and commits atomically. A stale rule result is
recomputed or rejected, and changing a rule never reinterprets a past
resolution. A clean automatic merge keeps enough evidence to explain and
reproduce it, without making a visible conflict.

The decision scenarios in [accepted ambiguity](conformance/accepted-ambiguity.json)
state these obligations as cases. A rule may record evidence fields of its own;
they never grant authorization or express human resolution intent, and
resolution evidence stays available for as long as its state is retained.
